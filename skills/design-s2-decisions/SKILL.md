# S2 方案决策

## 定位
- 输入：`brief.md`（S1 产出）+ design system 规范（组件 usage guideline）
- 输出：需求目录下的 `decisions.md`
- 下游：S3 方案发散、S4 原型、S5 Figma、S6 交付、S7 验收都从它推导，所以规则必须写到开发和验收能直接用的程度
- 分工：AI 出方案和推荐，设计师判断。AI 不替设计师做最终选择，也不替设计师假设业务规则

## 开工前
先读 Storybook 交互与文案规范（路径见 `Design-Pipeline/PIPELINE.md`「全局规范位置」），至少读 `START_HERE.md` 和 `patterns/FEEDBACK.md`。

## 流程
1. 读 brief.md，列出决策点清单（每条只写标题 + 一句问题），先让用户确认范围，不展开。
2. 逐个决策点处理：
   a. 把问题拆成两类。**规则**是行为逻辑：何时出现、谁能操作、状态如何变化。**呈现**是位置、布局、信息密度。常见错误是问题写的是规则，方案比较的却是呈现，要检查二者是否对得上。
   b. 规则：先写基础规则，再按下方清单推演边界情况，每个边界给 2–3 个选项、一个推荐和理由。
   c. 呈现：只有存在真实分歧时才列方向（A/B/C 各一句话）；否则跳过。这里**不选**，选定留到 S3 在 Claude Design 画布上并排看过再定（design-s3-explore）。
   d. 推荐依赖的业务事实，一律标【需确认】。
3. 每次输出的**最后**附一份「判断清单」（格式见下），设计师只需回复"编号 + 同意/改"。
4. 等用户判断后，再写入 decisions.md。
5. 每条决策都要写验收点：一句能被检查的话。写不出验收点，说明规则没写清，回到 2b。

## 边界情况清单（推演时逐项过一遍）
- 混合状态：多选的行状态不一致
- 空：无数据、无可用操作、无权限
- 切换：翻页、筛选变化、tab 切换后，状态保留还是清空
- 冲突：与现有元素（分页器、sticky header、drawer、弹窗）的空间或层级冲突
- 依赖：前置条件未满足时的表现
- 角色：不同 party role 或权限看到的差异
- 反馈：成功、部分失败、失败——每种写明用哪种提示（顶部 Message / 字段下方红字 / 页面提示条 / 确认弹窗，按 FEEDBACK.md 第一节选）；要弹窗的写明是确认弹窗（Yes / No）还是配置、提交类表单弹窗（Cancel / Confirm）

## 判断清单
每次输出的最后附上，让设计师能一眼扫完、回一行就把决策关掉。

要求：
- 一条一行，编号与正文的边界/呈现编号对应
- **用大白话写**，不用交互术语（写"关掉弹窗后文件还在吗"，不写"E1 模态关闭后的状态持久化策略"）
- 每行末尾带推荐结论，不是开放式提问
- 【需确认】的条目单独成组放在后面，标清楚要找谁——这些是业务事实，设计师也不一定能拍板

格式：
```
## 判断清单
回复"编号 + 同意"或"编号 + 改成 X"即可，没回的按推荐走。

1. 弹窗关掉后，文件和识别结果还留着，下次能接着确认 —— 推荐这样
2. 识别失败时弹窗不关，原地重试，文件不用重传 —— 推荐这样
...

以下要问业务，不是设计能定的：
A. 版本号什么时候算数：传上去就算，还是提交了才算 —— 和 PRD 写的不一致，找 PM
```

## 用户只回 "ok" 时
不要当作全部已审。标了【需确认】的条目单独追问；未标的视为采纳推荐，状态记为"采纳推荐（未逐条审）"。

**判断清单里没被回复到的条目同样按此处理**：按推荐采纳，状态记为"采纳推荐（未逐条审）"。不要因为用户回了其中几条，就把其余条目当作已逐条审过。

## 输出格式
```
## D-XX 标题
问题：
规则：
  - 逐条写，包括边界情况；依赖业务事实的标【需确认】
呈现：（无分歧则删掉此段）
  - A —
  - B —
  选定：（S3 画布上选定后回写） 理由： 画布：
验收点：
  - 一条对应一个可检查的行为
状态：待定 / 已定 / 已定（n 项待确认）/ 原型后改（附原因）/ 评审后改（附原因）
```
