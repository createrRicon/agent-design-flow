# S1 背景理解

## 定位
- 输入：BRD / PRD（md、html、pdf 均可）+ Figma 走查页链接（改版需求必填；新建模块可以没有）
- 输出：需求目录下的 `brief.md`
- 下游：S2（design-s2-decisions）以 brief.md 为唯一输入
- AI 角色是**提取**，不是分析：设计师的判断大多只在他脑子里，这一步的目标是把它写下来。AI 不能用推断代替这些判断

## 流程
1. 读 BRD，先判断需求类型：**改版**（有现有页面）还是**新建模块**。两者的"现状问题"写法不同，见输出格式。
2. 有走查页时，用 Figma MCP 读取：先用 get_metadata 定位截图 frame，再用 get_screenshot 查看。截图旁如有文字标注，优先采用。
3. 按下方格式起草 brief.md。每条内容标注来源：[BRD] / [走查] / [推断]。
   - [推断] 的条目必须经用户确认，确认后改成 [确认]
   - 没有标注的截图，AI 看到的"问题"一律标 [推断]；设计师真正在意的问题要靠追问得到
4. 追问缺口：每轮最多 3 个问题，按对 S2 的影响排序。优先问：
   - 现状问题里，设计师认为最严重的是哪个
   - 复用关系：复用什么、哪些地方必须不同
   - 业务规则中的"能不能"类问题（能否部分执行、能否跨角色操作等）。答不上的，放进"待确认"
   - 每个待确认问题都要问清楚"找谁"。不要留"待定"，设计师说不知道找谁的，就标"待定（设计师也不确定）"
5. 用户确认后写入 brief.md，末尾列出决策点候选清单，交给 S2。

## 写作纪律
- **brief 是摘要，不是 PRD 的副本。** 约束只收会影响交互决策的规则；其他规则写成"见 PRD §x.x"，不要全文照搬
- **一个信息只写在一处。** 设计上的缺口和待定项放进"决策点候选"，不要在"现状问题"里再写一遍
- **决策点候选不超过 8 条。** 先合并重叠项；纯规则类内容（例如某字段在哪里显示哪种格式）不算决策点，应该放进约束或留给 S6 交付
- 每个决策点标注：重心 / 非重心，以及被哪条待确认项阻塞

## 输出格式
```
# Brief: <需求名>
背景：BRD 一段话摘要
角色与核心任务：谁用 / 要完成什么 / 频率与规模
现状问题：
  改版 → 走查发现的问题，逐条列出，附 Figma 截图位置
  新建 → 目标用户现在怎么完成这件事（人工流程），以及其中的痛点；不知道就写进待确认，不要推断
复用关系：复用哪个页面或组件 / 差异点
约束：业务规则、技术限制、不在本次范围内的事项
待确认：问题 + 找谁确认（PM / 业务负责人 / 其他）
决策点候选：≤8 条｜标题 + 一句问题 + 重心/非重心 + 阻塞项
```
每条内容后附来源标签。

## 用户只回 "ok" 时
[推断] 条目不能因为一个 "ok" 就批量改成 [确认]。逐条列出，让用户逐条删改。
