# 评审修改

## 定位
- 评审不是固定的一站：主要在 S4 拿原型给大家点；S3 选方案时、S5 落 Figma 之后也可能有意见进来
- 输入：评审意见原文，格式不限（会议纪要或口头复述、原型 / Figma 评论截图或复制的文字、聊天记录），再加上 decisions.md 和当前阶段的画布 / 原型 / Figma 链接
- 输出：`review-log.md`，以及对 `decisions.md` 的回写
- 分工：AI 负责归类、对应到具体决策、标出冲突、给出处理建议；**采纳与否由设计师决定**

## 流程
1. 把原始意见逐条拆开。一句话里有两个意见就拆成两条。每条保留"谁说的"和原话摘要
2. 每条意见对应到 decisions.md 的某个决策（D-x）。对应不上的，标"新问题"
3. 每条意见标类型：
   - 规则（行为逻辑要改）
   - 呈现（看起来要改，决策不变）
   - 范围（要加或删功能）
   - 文案
   - 答复（回答了某个待确认项）
4. 主动检查三件事：
   - **冲突**：两个人的意见互相矛盾时，并排列出，不替设计师选
   - **关闭待确认**：意见里如果回答了 STATUS.md 的待确认项或某个【假设】，标出来，建议关闭
   - **连锁影响**：改动某个决策会牵连其他决策时（例如改了 B 会影响 A 的状态），写出牵连了哪些
5. 输出判断清单（格式同 design-s2-decisions），设计师回复"编号 + 采纳 / 不采纳 / 再议"
6. 设计师判断后：
   - 写入 review-log.md
   - 采纳的意见：decisions.md 对应条目改写，状态改为"评审后改"，注明 review-log 编号
   - 不采纳的意见：只记录在 review-log.md，并写明原因（之后被问到时有据可查）
   - 被回答的待确认项：在 STATUS.md 里勾掉
   - 列出要改的地方：S3、S4 阶段改方案画布或原型；S5 之后改 Figma frame（原型不再跟着改）

## 独立审查（替代原来的模拟评审）
用户要模拟评审、或原型做完还没有真实评审时使用。**不要自己审自己做的东西**：用 Agent 工具开一个全新上下文的子代理（general-purpose，不用 fork），它没参与设计，也不会被告知"为什么这样做"。

**只给它这些输入**（不给聊天记录、不给设计理由）：
- 原型：优先给本地 HTML 文件路径，让它用内置浏览器亲手点一遍（已发布的 Artifact 需要登录，子代理打不开）
- brief.md、decisions.md
- `Design-Pipeline/component-usage.md`、Storybook 的 FEEDBACK.md 和 CONFIRM_DIALOG.md
- 下面的审查清单和输出格式（原样贴进 prompt）

**审查清单**（改编自 Nielsen 启发式和 Impeccable 的 critique，去掉了审美类条目，审美以 library 为准）：
1. 入口可发现：核心功能不用别人教就能找到吗？要点几下？
2. 状态反馈：每个操作都有结果提示（成功、失败、处理中）吗？
3. 防错：删除、覆盖这类操作有确认吗？上限、重名能在提交前就挡住吗？
4. 出错能恢复：报错有没有说清原因和下一步？已经填的内容还在吗？
5. 能退出：每个弹窗、每个流程都能取消、返回、按 Esc 关掉吗？
6. 一致性：同一种动作是不是同一种 UI？按钮、弹窗、提示符合 component-usage 和 Storybook 规范吗？每个区域最多 1 个 Primary 吗？
7. 不靠记忆：做第 3 步时还要记得第 1 步的信息吗？选项多于 7 个时有没有分组？
8. 效率：每天都用的高频任务需要几步？有没有更短的路？
9. 业务用语：术语和用户平时说的一致吗？同一个东西在不同地方叫法一样吗？
10. 极端数据：空列表、达到上限、超长名称（取字数上限）、值失效、没有权限，各是什么样子？

**用三个角色各走一遍主任务**，每个角色列出卡住的具体位置：
- 高频老手：每天都用，嫌步骤多、确认弹窗多、没有快捷路径
- 第一次用的人：看不懂图标和术语，不知道下一步，不确定操作成功了没有
- 压力测试者：故意用空值、超长、满额、失效值、反复点击去试

**问题分级**：
- P0 阻塞：完成不了任务
- P1 严重：明显困惑或容易出错，评审前必须改
- P2 一般：别扭，但有绕过的办法
- P3 打磨：几乎不影响使用
- 拿不准时问一句"用户会不会因为这个去找客服或问同事？"会的话至少 P1

**不算问题的**：个人审美偏好；decisions.md 里已经定下的规则（除非给出新理由）；library 组件本身的样式。

**输出格式**（子代理按此返回）：
```
方法：独立审查（子代理） ｜ 结论：可进入下一阶段 / 改完再审 / 需要重想方案
做得好的：2–3 条
问题（最多 8 条，按严重程度排序）：
[P?] 位置 · 问题 · 为什么是问题（对应清单第几条或哪个角色）· 建议改法
角色卡点：每个角色 1–3 条
没能验证的：例如原型里点不到的状态
```

拿到结果后：
- 逐条转成判断清单交给设计师（流程第 5 步），每条标 [独立审查] 和级别
- 子代理开不了时，自己审也可以，但第一行必须写"⚠ 降级：同上下文自审"
- **[独立审查] 的意见不能关闭任何真实的待确认项或【假设】**；涉及业务范围、权限、优先级的问题（PM、业务、IT 的立场）只标出来，留给真实评审回答

## review-log.md 格式
```
## R-01 <一句话概括>
来源：<人 / 角色> · <会议 / Figma 评论 / 聊天> · <日期>
原话：<摘要>
对应：D-x　类型：规则 / 呈现 / 范围 / 文案 / 答复　级别：P0–P3（独立审查必填，真实评审可选）
处理：采纳 / 不采纳 / 再议　理由：
影响：<改了哪些决策 / 关闭了哪个待确认项 / 要改原型哪里或哪个 frame>
```
